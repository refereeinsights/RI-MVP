# CPO Review — HotelPlanner Booking Reconciliation, Lodging State & Routing Origin Addendum
**2026-08-30**

Reviewing the founder's "Slice 3.6B HotelPlanner Booking Reconciliation, Lodging State & Routing Origin" direction, treated as it says it should be: a reconciliation/scoping task, not build authorization. Verified every checkable claim directly against the vendor API doc, TI's live reconciliation code, and the actual database schema before responding — this document makes several real technical claims that turned out to be exactly right, one that needed a genuine correction, and it reopens a product-sequencing question I don't think should be resolved silently.

## What this document actually is, and the sequencing question it doesn't ask

This is framed as a Slice 3.6B addendum, but its substance is Phase 3B — "automatic hotel-origin suggestion" — which the founder explicitly deferred on 2026-08-28 pending "a real Corralio-owned HotelPlanner handoff feature." This document *is* that handoff feature's full design: attribution tables, a booking/lodging record, a planning-intent confirmation step, cancellation handling, multi-booking support, and routing-origin integration. That's fine as design work — getting ahead of scoping has been the right move all session — but it means this document functions as a proposal to un-defer Phase 3B, and it doesn't say so explicitly. Worth confirming that's the intent before this becomes a Stage 1 prompt, rather than treating it as a routing-origin footnote.

It also runs well past what ADR-033 (just landed) authorizes as pre-launch scope: "a contextual handoff into the existing HotelPlanner attribution/fee infrastructure when travel intent is detected — never a new, parallel hotel-commerce implementation." A handoff is one link with a token. This document is a full booking-lifecycle system — reconciliation on two cadences, a private booking table, planning-intent UI, cancellation suppression, multi-booking handling, revenue attribution. None of that is a "parallel hotel-commerce implementation" in the sense ADR-033 was guarding against (no payment, no checkout, no OTA), so it doesn't violate the ADR's letter — but it's a materially bigger build than "handoff," and ADR-031/033 both say fuller travel-commerce work should wait for the founder/product review after core planning value is proven. Recommend the founder state explicitly whether this is: (a) part of the launch-gate's narrow pre-launch slice, justified because a booking that silently doesn't come back into the plan is worse than not building the loop at all, or (b) genuinely V2/post-gate work being designed now so it's ready later. Either is defensible; leaving it unstated invites the same kind of drift ADR-031 exists to prevent.

Separately, factually: nothing in 3.6B has shipped yet. Checked the git log directly — the last real feature commit is Slice 3.6A (`b0495553`); Phase 1 (required arrival), Phase 2 (Arbiter audit), and Phase 3A (temporary routing origin) all exist only as filed Stage 1 prompts, none executed. Section 23 of this document explicitly and correctly says hotel lodging should "feed the same routing-origin contract as Phase 3A" rather than build a separate engine — good design discipline — but that contract doesn't exist in code yet. This document's routing-origin sections (23–25) have a hard dependency on Phase 3A shipping first, which should be stated as an explicit sequencing gate when this becomes a build prompt, not assumed.

## Real gap found: the confirmation-status field this document worries about is a different field than the one already locked

Section 16 says, correctly: "Do not assume the numeric `getClientSummary` status mapping is interchangeable with `getReport`." This is not a hypothetical caution — it's catching a real inconsistency in the already-committed design. `docs/reference/corralio-hotelplanner-attribution-design.md`'s locked reconciliation rule uses `status === 1` (numeric), empirically derived from a live `getClientSummary` diagnostic. But Section 10 of this same document (correctly) chooses `getReport` as the primary reconciliation mechanism, not `getClientSummary`. Checked `apps/referee/lib/hotelPlannerBookingSync.ts` directly: `getReport`'s `Status` column is read as a **string** (`getStr(row, headerIndex, COL.Status)`), not a number — a structurally different field from `getClientSummary`'s numeric one. The locked design's `status === 1` rule literally cannot apply to the mechanism this document (correctly) wants to use. This needs to be fixed before anything is built from either document, and I'll fold the fix into the design doc once this addendum is finalized.

The good news: this is mostly already-answered, not still-open. TI's own live production code already branches on real observed string values from real `getReport` data (`hotelPlannerBookingSync.ts` lines 618–620): `status.toLowerCase() === "confirmed"` and `status.toLowerCase().includes("cancel")`. That's first-party evidence from production, not a guess — it satisfies most of what Section 31 asks for without a new live diagnostic call. **Recommend, before running any new live API test: query `select distinct status from ti_hotel_bookings`** — TI already has real historical reconciliation data sitting in the database from months of daily syncs. That's free evidence, cheaper and lower-risk than a new live diagnostic, and will surface whether any status values beyond "confirmed" and the cancel-containing one actually occur (pending, no-show, modified, etc.) before Section 19's unknown-status handling is finalized.

What genuinely hasn't been exercised, and does need the live test this document asks for in Section 31: the `cancelledDateStart/cancelledDateEnd` query parameters themselves. Checked TI's actual cron (`apps/referee/vercel.json`, once daily at 5am, `hotelPlannerBookingSync.ts` line 102) — it only ever calls `getReport` with `purchasedDateStart/End`. The cancelled-date-range parameter this document's Section 11 depends on for the separate cancellation window is real and documented (verified directly against `docs/reference/hotelplanner-api-docs.md` line 1033, along with `includeCancelled`, default `true`, line 1041) — but it has never actually been called against this account. One bounded live test of that specific query shape, exactly as Section 31 requests, is the right next step before building the cancellation-reconciliation path.

## Real gap found: hotel location data doesn't come from the mechanism this document assumes

Section 9 says "if HotelPlanner reliably supplies property ID, address, latitude/longitude, retain the minimum trustworthy data required to use the confirmed lodging as a private routing origin." Checked the verified `getReport` column map directly (`COL` in `hotelPlannerBookingSync.ts`) and the existing `ti_hotel_bookings` schema: `getReport` returns `Hotel ID`, `Hotel`, `Hotel City`, `Hotel State`, `Hotel Country` — **no address, no latitude, no longitude, anywhere in this pipeline.** Coordinates do exist elsewhere in the vendor API (`multiPropertySearch`'s response includes `position.latitude/longitude` and `contactInfo.address1`, confirmed in the vendor doc), but that's a different, availability-search call, not the reconciliation-report call this design is built around. This means Section 9 and Section 23's routing-origin use case have a real, unaddressed gap: getting from "a confirmed booking's Hotel ID" to "a routable coordinate" requires either a secondary lookup (HotelPlanner's weekly `getDataFile` property export, cross-referenced by Hotel ID) or geocoding the city/state text, or a fresh `multiPropertySearch`/property-detail call at reconciliation time — three different approaches with different cost, freshness, and reliability tradeoffs that this document doesn't choose between. **This is a TEST FIRST item, not a BUILD item**: resolve which lookup path is cheapest and most reliable before writing a Stage 1 prompt for anything touching hotel-as-routing-origin. Everything else in this document (attribution, the booking record, cancellation handling, revenue) works fine without ever resolving this — only Sections 9 and 23–25 depend on it.

## What checks out cleanly

Sections 4–6 (attribution model, mapping table, attribution-vs-reservation-identity split) are consistent with the already-locked design and ADR-032 — no changes needed, and the explicit warning against storing the household UUID directly matches what's already decided. Sections 7–8 (booking record, data minimization) are sound; `ti_hotel_bookings`' actual schema (verified above) is a close, reusable template for the proposed `corralio_hotel_bookings` table. Sections 10–11 (getReport as primary mechanism, separate purchase/cancellation windows) are not just reasonable but vendor-confirmed — the separate-window design is a genuine improvement over the earlier generic 15–30-minute design, which never accounted for a booking cancelled well after its purchase window closed. Sections 20–22 (multiple bookings, booking ≠ automatic origin, an explicit "use this hotel" planning-intent step) are good product judgment — a silent auto-promotion from "booking exists" to "this is where we're leaving from" is exactly the kind of unearned-confidence UX this project's discipline elsewhere warns against, and I'd keep this even though it's scope growth. Sections 26–29 (revenue attribution, trigger context, privacy/RLS, worker isolation) don't introduce anything new relative to already-established patterns and are fine as stated.

The differentiated cadence itself (Sections 12–14: ≤30 min for new bookings during waking hours, four-times-daily for cancellations) is a sound, well-reasoned founder call — new-booking latency genuinely matters more to the parent's immediate experience than cancellation latency does, and the document is right not to force both onto one schedule for implementation symmetry. Flagging only the DST/cron-mechanics question it already flags itself as something engineering should resolve, not something to prescribe here.

## Verdict

**TEST FIRST**, not BUILD yet, on the whole. The attribution/booking/privacy/cadence design (Sections 4–8, 10–22, 26–29) is ready to become a Stage 1 build prompt once two real evidence gaps close: (1) one bounded live `getReport` call using `cancelledDateStart/End` + `includeCancelled` against a real cancelled attributed booking, confirming the field shapes Section 17 lists; and (2) a decision on how a confirmed booking's Hotel ID resolves to a routable coordinate, needed only for Sections 9 and 23–25. Before either, I'd want the founder to say explicitly whether this document is meant to un-defer Phase 3B now (ahead of the ADR-031/033 founder/product review) or is V2 design work being banked early — both are legitimate CPO answers, but the document doesn't currently say which.

One more thing worth surfacing plainly: this document was cut off mid-list in Section 32 (Tests), ending at item 16, "parse/upsert—". If there's more after that, worth sending the rest before this becomes a build prompt, since Section 32 is where the "fail closed" and idempotency discipline in Sections 16–19 actually gets locked down as verifiable behavior.
