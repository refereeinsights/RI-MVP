## 1. Mobile notifications

**What exists today: nothing.** Confirmed again this session — no service worker, no push subscription code, no `Notification` API usage anywhere in `apps/corralio`. `app/manifest.ts` is a complete, real Web App Manifest (name, standalone display, icons), which is necessary but not sufficient for push — it's the PWA installability layer, not the push layer.

**iOS (Safari/WebKit), verified against current sources:**
- Push requires the PWA to be **installed to the Home Screen first** — it does not work in an ordinary Safari tab, full stop. This is a hard precondition, not a nudge-able preference.
- Requires iOS 16.4+. Not available on iOS 17.4+ in the EU (a regional carve-out — likely immaterial to a US youth-sports product, but worth recording).
- Once correctly configured (VAPID keys, Apple's Web Push endpoint, a working relay path), documented delivery reliability reaches ~97%, comparable to native — but is reported as fragile to misconfiguration (one cited real-world case jumped from 60%→97% purely from fixing VAPID key setup). This is achievable, not automatic.
- Permission-prompt UX matters a lot: a "soft ask" that explains the value before triggering the native browser permission dialog reportedly gets meaningfully better opt-in (one case cited 72% after replicating a native-app-style onboarding flow) than asking cold.
- Deep-linking a notification tap into a specific in-app route (e.g., straight to This Weekend) is standard `notificationclick` service-worker behavior and works on iOS once installed.

**Android (Chrome), verified:** no install requirement in principle — push works from an installed PWA or, with lower persistence guarantees, an ordinary browser context. Reported real-world delivery reliability ~98%, "nearly identical to native." This is the easy side of the audit: build it once, it works.

**What this means for reach, stated plainly because it changes the channel decision:** iOS's install-gate means a meaningful share of parents — anyone who never taps "Add to Home Screen" — will **never** receive push, regardless of how well it's built. That's not a permission-UX problem to solve harder; it's structural. Given the founder's own final test is a parent who "connects both without leaving Corralio" and expects Corralio to reach back out, **email isn't a cost-minimization fallback here — it's the only channel that reaches the parents push structurally cannot.** I'm keeping email in the launch-required set for exactly that reason, not because it's cheap (see Section 5).

**Net new engineering surface required for any push notification, regardless of trigger:** a service worker (push-handling only — no offline caching commitment implied), VAPID key generation/config, a push-subscription table scoped to household/device with RLS matching the existing pattern, a soft-ask permission UX step, an iOS-specific install nudge (since push is literally inert until installed there), and a send-side function using a standard web-push library. This is well-trodden, standard Web Push API work — not experimental — but it is real, unbuilt surface area, comparable in size to a normal Corralio slice.

## 2. TomTom traffic-aware routing

**Quota — verified against TomTom's own pricing page, not assumed:** the founder's ~100K/month estimate is **materially wrong, and lower than reality**. TomTom's own `docs.tomtom.com/pricing` page lists the Routing API (Navigation category) free tier as **20,000 requests per month**, with paid tiers at 1M/5M/10M monthly requests beyond that, usage-based, "no costs upfront." The page also states **pricing is being revised effective July 2026** — i.e., possibly already in effect as of this month — so any number here should be re-confirmed against the live calculator before a contract is signed, not treated as locked.

**Exact paid-tier dollar pricing could not be independently verified to the founder's stated bar of "authoritative."** TomTom gates per-1000-request pricing behind an interactive calculator that a document fetch can't execute. A third-party API-pricing aggregator (not TomTom itself) cites a **$0.75–$6.00 per 1,000 requests** range "depending on service." I'm reporting that range with an explicit unverified-precision flag — it's directionally useful for the cost model below, but someone should run TomTom's actual calculator or get a quote before this becomes a budget line.

**Traffic-aware capability — verified against TomTom's routing-parameters documentation:** the Calculate Route endpoint takes a `traffic` boolean (use live traffic data or not) and mutually-exclusive `departAt` (default: now) / `arriveAt` parameters. This directly supports both "what if we leave now" and "what if we need to arrive by X" queries — both of the founder's proposed copy treatments are technically expressible in one API call each.

**Caching/storage terms — verified, and this is the important finding:** TomTom's developer terms (Clause 11.4) **prohibit storing or caching Results except client-side, bounded by the response's own cache-control headers, and explicitly prohibit "caching for the purpose of scaling results to serve multiple clients or users."** Read plainly, this rules out exactly the pattern Corralio's current routing architecture uses for OpenRouteService: compute a route once, write `estimated_drive_minutes`/`route_provider`/`leave_by_computed_at` into `corralio_events`, and serve that stored value on every subsequent page render indefinitely until the location changes. That's server-side, long-lived, cross-render storage of a provider "Result" — not the short, header-bounded, single-client caching the terms describe as permitted.

To be precise about what I'm confident of versus not: I'm confident the terms say what's quoted above, read directly from TomTom's own terms page. I'm **not** a lawyer and can't tell you with certainty whether a single household viewing its own previously-fetched route across multiple page loads within a short TTL counts as the prohibited "scaling to serve multiple clients/users" (my best read is no — that clause is aimed at reselling one paid call to many unrelated customers, not one family re-viewing their own weekend) — but real money and a vendor relationship ride on that reading being right, so **this needs an explicit answer from TomTom (sales/support) or counsel before implementation, not an inference from me.** This is a concrete, closeable item, not a permanent blocker — but it is a real precondition, and I'd treat skipping it as a mistake regardless of timeline pressure.

**Latency/reliability:** not independently benchmarked this session (would require a live API key and test calls, which I don't have and shouldn't provision without the founder's sign-off given Section 2's cost implications). Treat as an open item for whoever holds the eventual API key to confirm during implementation, not something this audit can certify.

**Expected calls per activated family/week — my own estimate, not sourced from TomTom or from real Corralio usage (none exists yet for traffic-aware routing), and should be replaced with real telemetry the moment any of this ships:** a family with ~4–6 weekend events across ~3–4 distinct locations, refreshed once when the weekend loads and again in a bounded pre-event window (the "traffic is building" moment), lands around **10–15 calls/family/week** (~45–65/month). This assumption directly drives the cost table below and is exactly the kind of number this team's own practice says to measure for real before committing to any caching/optimization strategy (the same discipline already applied to Slice 4.5's Overture radius/cap values and Slice 4.6's decision not to build a persistent route cache "before you have the number to justify it").

**Estimated monthly cost, using the 20K free tier (verified) and the $0.75–$6/1,000 range (unverified precision, bounding low/high):**

### 2A. Mapbox — alternative provider, added same day on founder input

The founder raised Mapbox's Directions API as an alternative worth checking before committing to TomTom. Verified directly against Mapbox's own pricing page and its current (July 21, 2026) Product Terms PDF — both first-party, not third-party aggregators:

- **Free tier: 100,000 requests/month** — five times TomTom's verified 20,000/month. This is a first-party number, not an estimate.
- **Paid tiers, exact and transparent (no calculator wall, unlike TomTom):** $2.00/1,000 for 100,001–500,000/month, $1.60/1,000 for 500,001–1,000,000, $1.20/1,000 above 1M, with a sales-negotiated discount above 5M.
- **No separate price for traffic-aware routing.** The same per-request price covers "optimal driving, walking, and cycling routes that take traffic and incidents into account" — one API, one price, unlike a design that would need to reason about a traffic surcharge.
- **An existing vendor relationship already exists in this monorepo.** `apps/ti-web` uses `MAPBOX_ACCESS_TOKEN`/`MAPBOX_SECRET_TOKEN` today (`lib/staticTournamentMaps.ts`, `api/cron/static-map-generator`) — but only for the Static Images API (venue map thumbnails), not Directions. This is a real procurement/billing advantage (same account, no new contract to stand up) with zero routing-specific operational experience behind it — nobody in this codebase has called Mapbox's Directions endpoint before, same as TomTom.
- **Caching terms, verified — stricter wording, but no practical difference given the design already adopted:** Mapbox's Product Terms Section 2.10.1: *"Customer shall not export, download, cache or store results from any request to a Navigation API."* No header-bounded exception at all — flatter than TomTom's Clause 11.4. Section 2.12 separately restricts "Traffic Data" (the underlying feed, not API results) to internal storage only under an active Order permitting that specific use case. **This does not conflict with the compute-on-demand, don't-persist design already adopted in Section 4 below** — it would have conflicted with the original persist-with-a-TTL design this document started with, which is exactly why that design was revised.

**Recomputed cost table using Mapbox's verified figures, same usage assumption as above (~45–65 calls/family/month):**

| Activated families | Est. monthly calls | Mapbox cost |
|---|---:|---|
| Pilot (~10) | ~500 | $0 — free tier |
| 100 | ~5,000 | $0 — free tier |
| 1,000 | ~50,000 | $0 — free tier |
| 10,000 | ~500,000–650,000 | ~$700–$1,040/month |

The 1,000-family row is the material difference: Corralio's entire pilot and early-launch volume plausibly runs free on Mapbox, while the same volume would already be in TomTom overage. **Recommendation: lead with Mapbox, not TomTom**, given the larger free tier, transparent (non-calculator-gated) pricing, no traffic surcharge, and the existing account relationship. TomTom remains a documented fallback if Mapbox's real-world routing quality or reliability disappoints once actually tested — that comparison still needs a live test with an API key, which nobody has done for either provider yet.

## 3. Product opportunity

Comparing the two proposed copy treatments against what's actually available:

- **"Leave in 20 minutes to arrive on time"** — this is a countdown claim. It requires a *live, current* route duration recomputed close enough to the actual departure moment that "20 minutes" is still true when the parent reads it, plus confidence that the event's start time and location haven't changed since the last check. Getting this wrong reads as Corralio actively misleading a parent about when to leave for their kid's game — a worse outcome than saying nothing.
- **"Traffic is building — leave by 7:08 AM"** — this is a state-change alert, not a live countdown. It tolerates more staleness (minutes, not seconds) and reads as directional guidance rather than a promise, which is a meaningfully lower accuracy bar to clear honestly.

**What would actually be required before either ships, stated concretely:**
1. **Accuracy**: a live traffic-aware call close enough to real-time that the estimate reflects current conditions — feasible per either provider's documented capability, and no longer contingent on an unresolved caching question now that the compute-on-demand design (Section 4) sidesteps both TomTom's and Mapbox's storage restrictions entirely.
2. **Refresh cadence**: a defined, bounded window (e.g., checked once in the ~2–3 hours before an event, not continuously) — continuous polling multiplies API cost roughly linearly and isn't obviously more useful to a parent than one well-timed check.
3. **Schedule state**: the event's start time and location must be confirmed unchanged since the last feed refresh before a leave-by push is sent — otherwise Corralio could tell a parent to leave for a game that already moved.
4. **Failure behavior**: if the live-traffic call fails or the household's daily external-call cap is already spent, the push must either fall back to the existing static estimate with honest "no live traffic" labeling (current Slice 4.6 card copy already does this) or simply not send — never silently show a stale live-looking number as current.

**Recommendation on the two copy treatments:** "Traffic is building — leave by X" clears a bar that's achievable for V1 — the caching question that gated this in the first draft of this audit is resolved by the compute-on-demand design (Section 4) and holds under either provider's terms. "Leave in 20 minutes" does not — it's a live-precision promise on top of infrastructure that has never been run in production for this product, and I'd want real accuracy data from the first treatment before shipping the second. This isn't overcaution for its own sake: a parent who's late to a game because a push told them "20 minutes" when it was actually 30 loses more trust than one who never got a push at all.

### 3A. Standard vs. Pro — added same day on founder question

Whether traffic-aware leave-by should be free (Standard) or paywalled (Pro) is a real open question this audit didn't originally answer. **Recommendation: Standard, not Pro, for V1.**

ADR-007 already framed this as a two-part conditional: traffic-aware routing "may become V2 and/or Pro only if user value **and** API economics justify it." This audit resolves the economics half favorably (Section 2A). It does not resolve the user-value half — nothing traffic-aware has shipped yet, so there's no usage evidence either way. ADR-011 is explicit about that situation: "Do not hard-code a permanent paywall, entitlement model, or final price before usage and willingness-to-pay testing." Gating an untested feature is exactly what that ADR warns against, not the cautious default.

It's also not currently buildable as a config flag: a full-repo check found **zero Pro/billing/entitlement infrastructure anywhere in `apps/corralio`** — no Stripe, no subscription-tier column, no paywall of any kind. Pro-gating this feature would mean standing up Corralio's entire monetization layer for the first time to gate one feature, before ADR-016's own Pro hypothesis ("exact Pro entitlements and pricing remain unapproved") has been tested on anything.

And it would fragment the launch experience: Weekend Ready and Schedule Change push are both landing free/standard (Section 5). Paywalling the traffic-aware upgrade to the same This Weekend card those pushes point back to would put a half-free experience in front of exactly the parents this launch is trying to activate — the founder's own Utility → Habit → Intent → Monetization sequence puts utility first, unconditionally.

Where Pro would make sense later, once real usage exists to justify it: something beyond a single-event estimate — live re-routing as conditions change mid-drive, per-team custom arrival buffers, or multi-stop/multi-child household routing. That's "planning complexity," the phrase ADR-016 uses for what Pro actually monetizes. A traffic-aware version of the existing single-event leave-by is core utility, not complexity, and belongs in Standard.

## 4. Architecture impact

**Can a traffic-aware provider fit behind the existing server-side, cost-controlled routing boundary?** Mechanically, yes, regardless of whether it's Mapbox or TomTom — `leaveBy.ts`'s `ExternalApiName` type is already a literal union (`"geocodio" | "openrouteservice"`) designed to be extended, and `corralio_events.route_provider` already stores the provider name as free text per row, meaning the schema was built provider-agnostic from the start. Adding a third provider (`"mapbox"`, per Section 2A's recommendation) is a small, well-contained change to an already-abstracted boundary. ADR-024 ("Routing Infrastructure Must Be Server-Side and Cost-Controlled") does not need to be reopened in principle — the new provider's calls would still be server-only, still capped, still audited the same way.

**What does need to change, and this is real architecture work, not a config flag:** the current reuse model treats a computed route as durable — valid indefinitely until the location changes (`isRouteFresh` only checks that the computed timestamp is newer than the geocode timestamps, with no time-based expiry at all). That's correct for a static, non-traffic route and is exactly why it was safe to build that way for OpenRouteService: `estimated_drive_minutes` today is a property of the *location pair* (home→field), so it's the same answer regardless of when it's asked, and reusing a stored value indefinitely is architecturally sound.

A traffic-aware duration is not that kind of fact. It's a property of the location pair **at the specific moment it was requested** — Saturday-morning traffic to a field bears no relationship to Tuesday-evening traffic to the same field, and shifts materially within a single morning. Treating it as event state to be written into `corralio_events` and read back later (even with a short TTL) is the wrong shape for this data, not just a staleness risk to manage.

**Revised recommendation, refined from the original draft of this section after further discussion:** don't persist a traffic-aware duration as durable event state at all. Fetch it live, on a specific trigger, only at the moments it's actually needed — immediately before sending a "traffic is building" push, or when a parent opens/foregrounds the app within the bounded pre-event window — and display it with an "as of [time]" stamp, the same honesty pattern Slice 4.6's cards already use for "no live traffic." Hold that fetched value client-side for a bounded window (on the order of 10 minutes) without re-asking even if the parent re-opens the view, and cap the number of refetches per event (2–3) rather than polling on a timer — a naive "refresh every 10 minutes while the app is open" design would generate far more calls per event than the once-or-twice-per-event pattern this cost model assumes. Nothing is written to a column another render or another day could read back as if it were still current. This is simpler than the freshness/TTL-on-a-persisted-column approach originally sketched here, and it sits comfortably against **both** providers' caching terms — TomTom's Clause 11.4 (Section 2) and Mapbox's flatter Section 2.10.1 prohibition (Section 2A) — since nothing is being stored beyond the ordinary single use of one response for one display or one push send. It also means the choice between the two providers doesn't hinge on caching-terms risk at all anymore; it hinges on the cost and account-relationship case made in Section 2A.

- The existing cross-event, same-household reuse-by-normalized-location optimization (`groupByNormalizedLocation`) stays exactly as-is for the static estimate; it simply doesn't apply to the traffic-aware path, which bypasses that reuse layer entirely and calls live each time it's invoked.
- ADR-024's own text already flags "provider selection and retention remain open" — this is exactly the open item that needs closing, via an ADR-024 amendment recording this compute-on-demand-and-discard policy for traffic-aware routing, distinct from the durable-reuse policy that stays correct for static routing. **I'd recommend amending ADR-024 rather than creating a new ADR number** — this is a refinement of the same decision ("routing must be server-side and cost-controlled"), not a new architectural stance, and a new number risks the same kind of citation drift already found in this project (ADR-030/033 cited in four documents but never landed in the canonical file — see the prior packet's Decisions Required #3).

**Net assessment:** no silent architecture replacement is needed or proposed. This is an additive provider plus one genuinely new concept (time-bounded freshness) that the existing static-routing design correctly never needed. That's a real, scoped piece of engineering work — I'd estimate it as comparable in size to Slice 4.3 (the original leave-by build), not a trivial provider swap.

## 5. CPO recommendation

| Item | Classification | Why |
|---|---|---|
| **Weekend Ready push** | **Launch required** | Content already exists (`weekendPlan.ts`); no routing/traffic dependency at all; this is the lowest-risk, highest-certainty proactive-feel win available. The only work is the push-infrastructure build itself (Section 1), which is standard, well-understood engineering. |
| **Email fallback/digest, sent alongside push** | **Launch required** | Not a cost-minimization move — a structural reach gap. iOS push is inert for any parent who hasn't installed to Home Screen; email is the only channel guaranteed to reach every activated household. Ship both together so "weekend ready" actually reaches the full activated base, not just the installed subset. |
| **Schedule Change push** | **Launch if technically clean** | The founder's own bar, and it's genuinely unmet today: there is no change-detection/diffing logic anywhere in `schedules/refresh.ts` — refresh currently upserts, it doesn't diff. "Technically clean" here means a small, bounded server-side diff on the existing daily refresh path (compare `starts_at`/location on upsert) actually gets built and proves reliable. If that lands cleanly alongside Weekend Ready, ship both together; if the diffing work slips, this one slips with it rather than shipping half-built. |
| **Traffic-aware leave-by (the underlying capability)** | **Upgraded to Launch if technically clean**, reversing this document's first-draft classification | The two things that made me call this post-launch — an unresolved vendor-terms/caching question and an unclear cost picture — are both resolved: the compute-on-demand design (Section 4) satisfies both providers' caching terms outright, and Mapbox's verified pricing (Section 2A) keeps pilot-through-1,000-family volume free and 10,000-family volume around $700–$1,040/month. What's left is a bounded, fully-in-Corralio's-control engineering task — comparable in size to the original Slice 4.3 leave-by build — not an external dependency on a vendor's legal terms. "Technically clean" here means: the live Mapbox call, the fetch-on-trigger/no-persistence pattern, and the "as of [time]" UI treatment actually get built and pass UAT alongside the rest of Slice 3.6 — if that slips, it slips post-launch same as Schedule Change would, but there's no longer a structural reason to assume it will. |
| **"Traffic is building" push** | **Upgraded to Launch if technically clean**, gated on the leave-by capability above landing first | Same reasoning — no longer blocked on anything outside Corralio's control, only on the build actually landing cleanly and on time. |
| **"Leave Soon" / live-countdown push** | **Post-launch**, and specifically gated on real accuracy data from the "traffic is building" treatment | This is the founder's own explicit conditional ("only if routing accuracy supports it") — it doesn't yet, because the infrastructure that would let it doesn't exist. Revisit after the first traffic-aware treatment has real-usage accuracy evidence, not on a timeline. |

**Highest-impact launch experience, concretely:** ship Weekend Ready as a real push notification (not email-only) alongside an email digest for full reach, build Schedule Change detection properly, and — updated from this document's own first draft, on better provider evidence — put real engineering time toward traffic-aware leave-by via Mapbox too, since neither the cost nor the terms objection that justified deferring it still holds. All three are now "launch if technically clean," meaning: build them, and let actual UAT/timeline outcomes decide what slips, rather than deferring the routing work by assumption before it's even attempted.

This reverses the prior packet's "email first, defer push" framing on the founder's explicit direction, and — same-day, on the founder's own follow-up questions about client-side freshness and Mapbox specifically — it also reverses this document's own first-draft "post-launch" call on traffic-aware leave-by. Both reversals happened because better evidence arrived, not because the underlying caution was wrong at the time it was written. "Leave Soon" is the one item that hasn't moved and shouldn't: it's gated on real accuracy data from a treatment that doesn't exist in production yet, which no amount of pricing or terms research can substitute for.
