## Findings (confirmed accurate against live verification)

**1. [Important, confirmed] What Fits does not use the household origin.** The original prompt repeatedly scoped the override to "leave-by/What Fits." What Fits has no origin concept at all today — building one would silently redesign completed Slice 4.6 behavior, an unauthorized scope expansion. Corrected: Phase 3A covers event leave-by only; What Fits is explicitly out of scope and its non-regression is now a named test and verification item.

**2. [Important, confirmed] Override scope was already settled, not an open audit question.** The original prompt asked Codex to audit and choose between per-event and household-wide models. The roadmap already places "per-event origin overrides" as the shape of this work. Corrected: Section 2 now states the per-event model as a decision — typed alternate address attached to exactly one upcoming event, current location request-scoped and never persisted, clearing/expiration affects only that event, no household-wide temporary origin ever.

**3. [Important, confirmed] Existing route storage cannot safely hold current-location results as originally scoped.** One route result is stored directly on the event row, and freshness is judged only by timestamp, with no field recording provenance. A temporary-origin route written through the same path would be indistinguishable from a Home-derived one on a later reload. Corrected: added a new Section 3 ("Data Model & Route-Cache Boundaries") requiring separate, provenance-tagged storage for temporary-origin results, an explicit prohibition on writing into the Home-derived cache columns, and a requirement that clearing/expiring an override restores the Home-derived route.

**4. [Important, confirmed] "Reuse the exact claim pattern" was inaccurate.** `claimOrigin()` is not a generic function — it hard-codes a write to `corralio_households`' own Home columns and cannot safely claim an event-scoped override without either colliding with Home's claim state or silently requiring new columns it doesn't know about. Corrected: the prompt now specifies reusing validation, concurrency semantics, quota reservation, provider adapter, sanitized logging, and failure classifications — but requires a new, narrow claim/persistence boundary for the event-override target, never calling `claimOrigin()`/`clearOriginClaim()` directly.

**5. [Important, confirmed] No database-verification gate was specified, despite a migration being the likely outcome.** Corrected: added Section 6 requiring Stage 1 to stop at `SLICE 3.6B PHASE 3A READY FOR DATABASE VERIFICATION` when a migration is needed (code + unapplied migration + catalog verifier + rollback-only behavioral verifier), with bounded UAT and final completion only after a human applies the migration — the same staged discipline already used for Phase A+B's Stage 1 database gate.

**Additional corrections accepted and folded in**, all independently plausible given the above and not contradicted by anything found in the repository: current-location coordinates need no reverse geocoding and should route directly through the existing ORS provider; browser coordinates are caller-supplied private input, not trusted identity evidence; exactly one fresh user-gesture geolocation request, never `watchPosition`/background polling/reload-reuse/analytics/raw-coordinate logs; an explicit retention rule for alternate addresses (delete after the associated event passes, plus a small grace period); temporary-origin data must never participate in venue matching, provisional venues, Overture evidence, or public venue intelligence — extending `CORRALIO_SECURITY_PRIVACY.md`'s existing Home rule; "Home is always available" corrected to "Home remains selectable; show the existing setup requirement if ungeocoded, rather than fabricating a route"; the long HotelPlanner/API tangent in the original Section 1 trimmed to a single pointer, since it has no bearing on Phase 3A; offline tests cannot prove RLS, so real rollback-only database verification is required for authorization/cross-household denial/expiry/cleanup; UAT cleanup must explicitly cover event overrides, any transient route records, provider ledger rows, household/Auth fixtures, and zero retained current-location coordinates.

## Disposition

`docs/prompts/corralio-slice-3.6b-phase3a-temporary-routing-origin-prompt.md` corrected in place (superseded-in-place, not archived separately, since the original was never dispatched and shipped nothing).
