## D. Slice 4.4B — Provisional Venue Creation from Published Schedules (Shipped)

Translates the CPO's original B decision ("Accept With Changes" on automatic venue creation) into a scoped slice. Original decision reasoning: automatic creation is directionally right, but not into `public.venues` directly and not on today's conservative match-or-unmatched logic alone, because `public.venues` feeds a live, individually-routable, SEO-indexed public surface (`apps/ti-web/app/venues/[venueId]` plus a full sitemap system) — a materially different, harder-to-unwind risk than anything Corralio has written so far.

**Evidence threshold, refined after discussion:** the bar for *creating* a provisional venue is deliberately low — source trust is recorded but not required to create. The bar for *promoting* a provisional venue to canonical/public is where strong source/corroboration requirements actually live, assigned to a separate, later validation/promotion slice (not yet designed). This is correct because the risk this whole decision exists to contain — public exposure of unverified data — is fully contained at the isolation boundary, not at the creation gate. Over-gating creation bought nothing except lower venue-identity coverage, which directly undermines Slice 4.5's dependency on shared venue identities (Section E below).

**Mandatory regardless of the lowered creation bar:**
- Privacy exclusion (reuse Slice 4.4's classification as the *only* privacy gate — no second parallel implementation).
- Facility/public-place validation beyond Geocodio address-validity alone — Geocodio will happily geocode a private residence. Interim signal: a name-pattern heuristic (contains "field," "complex," "park," "gym," "arena," "courts," or similar). Stronger signal once Slice 4.5 ships: cross-check against Overture Places for a matching recreation/sports-category POI.
- Duplicate prevention, reusing/hardening the conservative matcher's logic — its "any ambiguity resolves to no match" discipline was tuned for a world where a false negative was free (an unmatched event still renders leave-by fine); it isn't free anymore once "no match" can trigger a new provisional-venue creation instead.
- Provenance capture, queryable by feed/time-window specifically, so a bad validator or bad source can be bulk-reverted rather than corrected one venue at a time.
- Full reversibility — deleting an unindexed provisional row is cheap; nothing about this design should ever make it expensive.

**Structural isolation — implementation requirement, not a preference:** provisional venues live in a separate Corralio/TI-shared table, not a `status='provisional'` flag on `public.venues`. A flag is one forgotten `WHERE status = 'public'` away from a leak into `venues_public`, the sitemap generator, or a future admin view nobody thought to filter — exactly the failure class that's expensive to catch after the fact. A separate table structurally can't leak that way, since nothing queries it unless it explicitly knows to. A provisional venue can never appear in public TI/RI surfaces and can never overwrite canonical `public.venues` data.

**No venue directory in Corralio, at any stage.** A venue identity — matched, provisional, or eventually promoted — is backend plumbing, never a browsable entity inside Corralio. Slice 4.4's matching is invisible to the parent by design; 4.4B's provisional venues are never rendered anywhere in Corralio; Slice 4.5 (below) surfaces POI results tied to an *event*, never a venue profile or directory. This is a standing product boundary, not a Slice 4.4B-specific rule — worth keeping explicit as this architecture grows so a "view venue" affordance doesn't quietly creep in later.

**Instrumentation:** extend Slice 4.3's usage-report pattern (a read-only script, not a dashboard) to report venue-identity coverage — (geocoded sports events with a matched or provisional venue) ÷ (all successfully geocoded sports events) — plus a duplicate/near-duplicate rate, given the creation bar is intentionally loose. This coverage number is the readiness gate for Slice 4.5, and the improvement lever if coverage is poor is 4.4/4.4B matching quality — never a parallel household/event-specific POI path that would mask the gap instead of closing it.

**ADRs:** ADR-008 ("Corralio does not directly create or modify canonical venue records") has been revised in place in `docs/corralio/CORRALIO_ARCHITECTURE_DECISIONS.md` as a documentation correction — it now states explicitly that provisional-venue creation and evidence-attachment (4.4B/4.4C) are a distinct, already-implemented authority from canonical writes, and that the canonical-write prohibition itself is unchanged: nothing in 4.4B or 4.4C ever writes to `public.venues`. ADR-021 ("Promotion requires trusted review or validated automation") was left untouched, per instruction — it already anticipated this path and now doubles as the pointer to the reserved promotion slice (Section E2). **Status: done, verified in the file.** (Note: this edit, along with the `CORRALIO_PRODUCT_ROADMAP.md` numbering fix, remains uncommitted in the working tree as of this update — a housekeeping item for Codex/the founder to commit, not yet actioned by me.)

**Sequencing:** does not gate Slice 4.4 or leave-by (4.3). Is a soft prerequisite for Slice 4.5, because Overture POI enrichment attaches to reusable shared venue identities rather than household-specific event coordinates — an efficiency and flywheel choice (enrich a venue once, every household sharing it benefits) that trades away a coordinate-only fallback path deliberately (see Section E).

**Shipped:** `corralio_provisional_venues` table, `corralio_event_venue_matches` mutual-exclusion table, `corralio_create_or_reuse_provisional_venue_v1` and `corralio_suppress_provisional_venue_v1` RPCs — structurally isolated, canonical-first race-checked, cross-household reuse supported. I found no evidence anywhere in this codebase of a booking-completion webhook or postback from HotelPlanner. Two honest paths exist, neither yet chosen: (a) treat the outbound click itself as a soft, clearly-caveated signal ("family likely traveling near Venue X this weekend") for Nearby/leave-by purposes, accepting it's inferred, not confirmed; or (b) ask the parent to explicitly confirm back in Corralio after booking ("Save this hotel to your weekend plan?"), which is higher-fidelity but depends on the parent bothering to do it and adds a UI step. Which path is right — and whether HotelPlanner's affiliate program offers any confirmation feed at all, which is a vendor question, not an engineering one — should be resolved when Slice 4.8 actually gets its formal write-up, not guessed at now.

**Classification: no change from Section H/"Still open" below.** This stays inside Slice 4.8's already-pending decision note and Codex-ready prompt — gated behind the founder/product evidence gate (ADR-031/033) clearing via the pre-launch pilot test, same as before.
