# CPO Review Addendum — SMS-First Reframe of the HeySammi Review

**2026-08-30 · Chief Product Officer**

This is a delta document, not a rewrite. The revised prompt sharpens three things the original `2026-08-30-cpo-review-heysammi-competitive-signal.md` treated more loosely: SMS as the *primary* channel (not co-equal with email), push as strictly optional/supplemental (not a default first surface), and several mechanics that weren't specified before (SMS message discipline, specific account/identity edge cases, calendar-output cannibalization risk). Most of the original review's evidence and verdicts stand unchanged — this document says explicitly where they hold, where they need correction, and answers what's newly asked. Read alongside the original; this doesn't restate its competitive table, ingestion-scope reasoning, or privacy baseline where nothing has changed.

**One new piece of repository evidence, gathered for this addendum:** Corralio's Supabase Auth today is entirely email-based. `SUPPORTED_OTP_TYPES = ["email", "magiclink", "recovery"]` (`apps/corralio/lib/authCallback.ts:3`) explicitly excludes phone, and every auth path in the repo (`signInWithPassword`, `signInWithOtp`, `resetPasswordForEmail`) is email-keyed — grepped directly, no phone-based Supabase auth exists anywhere in `apps/corralio`. This matters for Section 4 below.

**Resolution (2026-08-30, same day): the founder has overridden Section 4's implicit conclusion.** Section 4 below treated "email is the only path to the full web experience today" as a constraint this work would have to design around. The founder's decision is the opposite: email must not be required for account creation, authentication, household access, or the full web experience at all — this repository fact was evidence about today's implementation, not a product constraint, and the SMS-first work should change it. See `2026-08-30-cpo-investigation-phone-first-authentication.md` for the full audit and migration design (headline finding: household creation is already keyed purely on `auth.uid()` with no email-specific step, so adding Supabase native phone auth via a Send SMS Hook is additive, not a parallel system). Section 4 below is preserved as written for its still-correct sub-answers (verification-as-dedup, recovery-policy reuse, the authentication-vs-authorization distinction) — only its "email is required for web login" framing is superseded.

## Where the original review needs correction, not just addition

**The daily-brief delivery sequencing in the original Section 5 assumed push as an acceptable first surface. That's now wrong for the population this revised prompt is about.** The original said the brief's "first delivery surface can be push... or an in-app 'Today' view." That's still true for households who already went through Corralio's existing web onboarding — they have the PWA and, per Slice 3.6A, may have granted notification permission, so push is a reasonable near-term surface for *them*. But the entire premise of this revised prompt is a second population: prospective families with no client installed and no notification permission, who by definition cannot receive push at all. For that population, push isn't just non-primary, it's structurally unavailable until they've already installed something — which is the exact chicken-and-egg problem SMS-first is meant to solve. Treat these as two separate delivery tracks: the existing pilot cohort keeps push as a fine interim surface for the brief once 3.6B Phase 1 ships; the new SMS/email-first cohort's first-ever brief has to arrive over whichever channel they arrived through (SMS or email), which only exists once Phase A–C of the channel work lands. Don't let "ship the brief on push first" read as the answer for both.

**Everything else in the original review — the competitive table (Section 1), the "don't copy coach-cold-texting or team-admin bundling" guidance (Section 2), the minimum ingestion scope (Section 4 there), the freshness numbers (Section 7), and the core privacy principles (Section 9) — holds as written.** The rest of this addendum covers what's genuinely new or needs expansion.

## Updated answers to the 14 requested outputs

**1. Competitive assessment — unchanged.** See original Section 1. The SMS-first framing doesn't change any of HeySammi's verified-vs-claimed facts.

**2. Corralio competitive response — unchanged, with one sharpening.** The original's "lean into cross-child, cross-team household planning, not ingestion novelty" holds. Add: HeySammi's own architecture is also SMS-primary for the parent side (its "no app, no account" pitch *is* an SMS-first activation claim), so adopting SMS-first here is matching a real design choice HeySammi made, not inventing a new hypothesis in a vacuum — the differentiation still has to come from what happens once the message engine exists (real leave-by/conflict math instead of screenshotted mockups), not from the channel choice itself.

**3. SMS-first channel architecture — refined.** The original's Phase A (verified channel identity) → B (deterministic ingestion) → C (notification delivery) → D (future send-first) sequence is unchanged in shape. What changes is which leg goes first and why: the original's "smallest launch-worthy version" picked email first because Resend's inbound webhook is faster to stand up than clearing A2P 10DLC. That's still the right execution call, but it should not be read as demoting SMS. **Recommend stating this explicitly wherever this work gets scheduled: SMS is the primary strategic destination; email ships first only because of an external carrier-registration lead time, not because it matters more.** If that distinction isn't written down, "build email first" quietly drifts into "email is the plan," which contradicts the founder's actual hypothesis.

**4. Account/identity model — this needs real expansion; the original treated it as one paragraph.**

The new repository evidence changes the shape of the answer: since Corralio's web auth is entirely email-keyed today, a verified phone number cannot, by itself, become a working login credential without adding phone-based Supabase Auth — a real, identifiable technical decision this review is not making for you. That reframes "lightweight channel association" more precisely:

- *Can a phone number begin an identity relationship without becoming household authorization?* Yes — verification (send-code/confirm) proves reachability, nothing more. Household authorization stays governed by whatever mechanism already grants it (today, email-based Supabase Auth). This is consistent with, not a new instance of, the "possession isn't authorization" principle already in `CORRALIO_SECURITY_PRIVACY.md`.
- *Can a parent send a schedule before completing conventional signup?* Yes, if the flow captures (or defers capturing) an email at the point of first real value, not before. A minimal household record can exist keyed to a verified phone, with email capture deferred to "see your full plan on the web" — this avoids inventing a phone-only account model while still letting the SMS interaction start before signup friction.
- *Can an SMS-originated user transition into the full web experience?* Only via email today, because that's the only auth path that exists. The practical flow: prompt for an email at whatever moment the parent wants the web plan, send the existing magic-link/OTP flow to it, and it's a normal Corralio login from there. Adding phone-based Supabase Auth is a separate, deferred option if the founder wants a phone-only account someday — not assumed here.
- *Duplicate phone numbers/emails across households:* verification is the natural dedup mechanism — a number or address can only be verified into one household's channel-identity slot at a time, because verifying it into a second household requires the same send-code/confirm step, which the first household's owner would have to complete, not a stranger. No separate uniqueness logic needed beyond what verification already provides.
- *Household recovery / changed phone numbers:* this is the same unsolved problem as "household invitation and recovery policies," already listed as an open question in `CORRALIO_SECURITY_PRIVACY.md`. Recommend folding channel-identity recovery into that existing open item rather than designing a parallel, SMS-specific recovery flow.
- *Minimum verification before private schedule information is returned:* the verified channel itself (phone confirm, or an authenticated household's own email alias) is the minimum bar — this is unchanged from the original review, and nothing in the new sub-questions lowers it.

**5. Minimum ingestion scope — unchanged.** See original Section 4. Add the founder's new caution directly into any customer-facing copy: **"send your schedule" should never appear unqualified.** Recommend copy that names the two supported shapes explicitly — a calendar link, or an `.ics` file — so the invitation doesn't silently imply PDF/screenshot/prose support that doesn't exist. This is a copy discipline point, not a scope change, but it's worth stating as its own rule since the founder called it out specifically.

**6. Daily/event-day brief — unchanged content recommendation, corrected delivery-sequencing note above.** Still gated on 3.6B Phase 1; still a small build once Phase 1 lands; the only change is not treating push as a universal first surface (see correction above).

**7. SMS message discipline — new, not covered in the original review.**

Recommend the working principle as stated in the prompt — SMS for decision/action, email for detail, web for the full plan — become an explicit written product rule, not an implicit convention, since it's the thing most likely to erode message-by-message without one. Concretely:

- Design every outbound SMS template to fit one GSM-7 segment (160 characters) as the default target, treating a second segment as an accepted exception for messages where clarity would otherwise suffer (e.g., a schedule-change alert with an old and new time) — not a hard ceiling.
- Avoid emoji and most non-ASCII punctuation (curly quotes, em-dashes) by default, since a single such character forces the whole message into UCS-2 encoding, dropping the per-segment limit from 160 to 70 characters — a much easier limit to blow through by accident than to think about deliberately.
- Instrument **billed segments**, not message count, from day one — this is a real COGS line, and "average segments per delivered SMS" should be a tracked metric (Section 13) before volume exists, not retrofitted after.
- Treat STOP/HELP/START keyword handling as non-negotiable table stakes for any US SMS program, independent of anything else built — this isn't a product decision, it's a carrier/TCR requirement for A2P registration to succeed at all.
- Beyond STOP/HELP, recommend distinguishing two different things both called "two-way SMS": (a) deterministic reply-keyword handling (e.g., replying "Y" to confirm a detected schedule, or a numbered choice) — small, scoped, arguably necessary for a usable ingestion-confirmation flow, and (b) open-ended conversational SMS — categorically bigger, still correctly deferred per the original review's pushback on "eventually interactive SMS assistance." Don't let (a)'s near-term necessity quietly become license to build (b).

**8. Calendar output — same recommendation, new risk explicitly evaluated.**

The original review already flagged the build cost correctly (no ICS-generation code exists in `apps/corralio` today; `ti-web`'s implementation is a reusable pattern, not shared code). New to this addendum: the founder specifically asked to weigh calendar output's effect on activation, retention, and referral against the risk that it **reduces reasons to return to Corralio.** That risk is real and specific: once a family's schedule lives in Apple/Google Calendar, the calendar app becomes the thing they check, and Corralio's own "weekly returning families" metric — still the primary V1 success measure per the ambient-strategy response's Section 3 — could decline even while the household is getting real value. The original review already recommended this pending an ambient-equivalent measurement framework before leaning on any "don't need to visit" thesis; that recommendation directly covers this calendar-output-specific version of the same risk. Recommend the same gate: build calendar output as a candidate, but don't ship it as a promoted feature until there's a way to tell whether a household that stops opening the PWA because the calendar feed suffices is a retained customer or a quietly churned one.

**9. Freshness model — same numbers, new linkage.** The original's 4-hour cron / 3-hour eligibility / 5-minute manual-refresh-cooldown findings (`vercel.json:4`, `refresh.ts:10,14`) are unchanged. New: the founder asks whether refresh behavior varies materially by source and whether that belongs in the Schedule-Source Compatibility & Evidence Matrix. It should — that matrix (filed, non-blocking, ready to execute per `CORRALIO_CPO_EXECUTION_STATE.md`) is exactly the right home for per-source freshness variability, rather than opening a separate freshness-specific investigation. Recommend folding "does this source's freshness/refresh behavior differ from the baseline cron model" into that matrix's existing scope rather than treating it as new work.

**10. Vendor requirements — expanded, still no selection.**

The original's shortlist (SMS: Twilio/Telnyx/Plivo; email: Resend/Postmark/SES) and its caveat that all figures come from secondary sources, not vendor documentation or a spike, stand unchanged. Two additions the revised prompt specifically calls out that the original didn't size:

- **Two-way SMS requirements**, per the distinction in Section 7 above: at minimum, STOP/HELP/START handling (table stakes for A2P approval) and a simple deterministic reply-keyword parser (for ingestion confirmation). All three shortlisted SMS vendors support inbound webhooks, which is what this needs — the differentiator is how much of STOP/HELP compliance each handles automatically versus requiring the team to implement (a real spike question, not answerable from marketing comparisons).
- **Email attachment handling for `.ics` files**: inbound-webhook parsing of attachments with size limits and content-type validation is a real security surface (a malformed or oversized attachment shouldn't be able to affect the ingestion pipeline) — this belongs in the same spike as the rest of the vendor evaluation, not assumed safe by default. Resend's inbound feature was confirmed (prior investigation) to parse attachments with metadata and temporary download URLs; whether that safely bounds size/type needs direct verification, not inference from a landing page.

**11. Privacy/security implications — unchanged, one addition.** The original's coverage (message-content minimization, sender-identity-isn't-authorization, the iCal-subscribe-token treatment as a public-sharing case, bounded retention) all stands. Addition: since children's schedules, teams, locations, and event details are explicitly named in this revised prompt as sensitive private household data (already true in `CORRALIO_SECURITY_PRIVACY.md`), any SMS message design (Section 7) should be reviewed against the same field-minimization principle applied to public shares — a 160-character SMS visible on a shared or locked family phone screen is, if anything, a lower-control surface than a PWA screen behind auth, so child-name/location minimization matters at least as much there, not less, despite the message being short.

**12. Roadmap recommendation — unchanged from the original's table, with the SMS-primacy labeling addition from Section 3 above and the freshness-matrix folding from Section 9.** No change to the 3.6B critical path. Daily brief still sequences immediately after Phase 1. Email-leg ingestion still ships before SMS-leg ingestion for execution-speed reasons — now explicitly labeled as a sequencing choice, not a strategic one.

**13. Metrics — one addition to the original's funnel.** Add **SMS segments billed** as a tracked metric per the founder's explicit list, alongside "average segments per delivered SMS" from Section 7. Both should be instrumented from the first SMS send, not retrofitted once volume makes the COGS question urgent.

**14. Repository/documentation impact — same list as the original's Section 12, plus:** `CORRALIO_SECURITY_PRIVACY.md`'s SMS section should gain the message-discipline rules from Section 7 (segment target, STOP/HELP as non-negotiable, child-data minimization in short messages); the Schedule-Source Compatibility & Evidence Matrix's scope note should be updated to include per-source freshness variability (Section 9); and wherever the email/SMS channel work gets formally scheduled, the SMS-primary/email-first-for-execution-reasons distinction from Section 3 should be written down explicitly so it isn't lost in translation between this review and a build prompt.
