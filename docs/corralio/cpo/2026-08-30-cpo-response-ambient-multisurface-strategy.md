## The one thing to resolve before anything else in this document matters

**The pricing table puts traffic-aware leave-by under Pro. That reverses a decision this project already made, with reasoning, and already committed to the repository.**

- `dc10c888` — "traffic-aware leave-by ships Standard, not Pro, for V1" (already in git history, predates this session).
- The 2026-08-27 notification/traffic-routing audit, Section 3A, reasoned through this explicitly: ADR-007's "may become V2 and/or Pro only if user value **and** API economics justify it" — the economics half is resolved favorably (Mapbox's free tier and pricing), the user-value half has no evidence either way (nothing traffic-aware has shipped), and ADR-011 is explicit that gating an *untested* feature behind Pro is exactly the wrong default. There is also no entitlement/billing infrastructure anywhere in `apps/corralio` today — Pro-gating one feature would mean standing up the entire monetization layer for the first time to gate this alone.
- Two messages ago, at your own request, I corrected `CORRALIO_FOUNDER_MENTOR_HANDOFF.md` because it still listed traffic-aware leave-by as a Pro example — the correction reads: *"Traffic-aware leave-by itself is no longer a Pro hypothesis — it shipped as a V1 Standard-tier decision... Pro's traffic-adjacent upside, if any, is downstream of it — live re-routing mid-drive, multi-stop/multi-child routing — not the base capability."*

This new pricing table puts it right back under Pro, three exchanges after that correction shipped. I'm not assuming this is a mistake — you may have a real reason to reverse it (maybe the ambient-surface thesis changes the calculus: if SMS becomes the primary way most families experience leave-by, "basic" vs. "traffic-aware" SMS content might be a cleaner Standard/Pro line than it was for a single PWA card). But I'm not updating any canonical document to match this table until I hear which one it is. If it's deliberate, tell me why the prior reasoning (no evidence to gate an untested feature, no entitlement infra exists, launch-experience fragmentation risk) no longer applies. If it's not deliberate, the fix is just to move "traffic-aware leave-by" back to Standard in this table and keep Pro's traffic-adjacent story to what it already was: live re-routing mid-drive, multi-stop/multi-child routing.

## What's genuinely new here versus the ingestion review two messages ago

That review covered the *ingestion* half of this (email/SMS as entry points, common pipeline, unclaimed-session claim flow) — verdicts there are unchanged and this document doesn't add new evidence to revisit them. What's new in this message: the "don't need to visit Corralio.com" thesis itself, elevating iCal-publish to a headline value prop, reframing SMS as an ongoing surface rather than an acquisition channel or a notification afterthought, the proactive-travel-intent vision, and the pricing/tier split.

## Where this is strong

- **Publishing a Corralio iCal feed** is the single best idea in this document, and it was already the one thing I flagged last time as "worth a look, likely a much shorter path to real value than anything else." This message makes the case better than I did — "send us your schedules, subscribe to one feed" is a genuinely clean value proposition. It needs no new claim/auth architecture (the household already exists and is authenticated), reuses calendar-serialization capability this project already has proven (ADR-004), and is outbound-only, which sidesteps every privacy question this session has spent time on for inbound channels. **I'd move this from "worth a look" to an actual near-term candidate** once the 3.6B critical path clears bandwidth — it doesn't need to wait on any ingestion evidence at all, since it works from schedules Corralio already has today.
- **Travel discovery available to Standard, not gated behind Pro** — consistent with the already-accepted model (ADR-015/016), no objection.
- **Framing $49.99/year as an explicit, named hypothesis** rather than a committed price is the right discipline (ADR-011) — the number itself isn't the issue, the traffic-aware placement is.
- **"Ask whether they need lodging unless Corralio actually knows booking state"** is a good, specific instruction that prevents an easy, embarrassing mistake (assuming no booking exists and being wrong).
- The Standard/Pro split for schedule-change messaging — a basic "your calendar was updated" (Standard) versus richer "impact" analysis (Pro) — is coherent and, usefully, resolves part of an already-open question: `CORRALIO_CPO_EXECUTION_STATE.md`'s Open Decision #2 (schedule-change push has no recorded tier or disposition) could close on this basis, if you confirm that's what you mean.

## Where I'd push back or want an explicit answer before treating this as decided

**"A family should not need to regularly visit Corralio.com" changes what success looks like, and the project has no way to measure the new definition yet.** Today's entire measurement framework is built around visits: ADR-012 ("Build for Recurring Weekend Usage" — "product structure and metrics optimize for recurring weekly family utility"), the roadmap's V1 success measures ("This Weekend viewed," "weekly return"), and the stated primary metric ("weekly returning families with multiple connected schedules") are all, implicitly, PWA-session metrics. If a household that never opens the PWA again — because their calendar app and their texts already tell them what they need — counts as a *successful* Corralio customer under this thesis, that's a real redefinition, and right now there is no instrumentation that would tell you whether that household is thriving or has quietly churned. A calendar feed fetch and an SMS delivery are both things you can technically log, but neither is built, and neither has been discussed as a retention signal until this message. I'd treat "how do we measure ambient success" as a real open problem to solve *before* leaning on this thesis to justify de-prioritizing PWA engagement — not an afterthought once the surfaces exist.

**This is still a zero-evidence assumption being asked to carry more weight than the last version of it.** Two messages ago, the same underlying idea ("send-first beats signup-first") was scoped to ingestion and I recommended testing it manually before automating anything. This message uses the same untested assumption to justify a broader architecture *and* a monetization split. I'd keep those separated: writing "ambient/multi-surface" into the roadmap as a named long-term thesis is reasonable and costs nothing. Using it to decide pricing tiers or to deprioritize the PWA's primacy is not yet earned — nothing about it has been tested, including the cheapest version (the manual concierge pilot I proposed last time hasn't run).

**"Eventually interactive SMS assistance" is bundled into Pro's feature list next to "richer briefings" and "advanced conflicts," but it's a categorically different, much bigger thing** — two-way SMS implies some form of natural-language intent handling, not a richer version of a one-way message. I'd pull it out of the Pro bullet list entirely and treat it as its own far-future, evidence-gated idea, so it doesn't quietly become an assumed part of "what Pro includes" before anyone has scoped what it would take to build.

**The proactive travel-intent SMS example is a good North Star, several unbuilt capabilities away from real.** "Tournament in 6 weeks, 214 miles away, need a hotel?" requires tournament recognition, persistent geocoding, home/base distance classification, and timeline awareness all working together — that's ADR-033's Contextual Intelligence slice (not built) plus Phase 3B (currently at the evidence-diagnostic stage). Nothing wrong with the example as illustration; worth being explicit that it's illustrating a destination, not a near-term deliverable, so it doesn't get treated as something to scope next.

**Elevating SMS to "a product surface" is itself a roadmap-sequencing decision, not just repositioning.** The roadmap today gates SMS entirely behind Phase 3 and behind push+email proving the retention hypothesis first. This message writes about SMS as though that evidence already exists. If the intent is to formally move SMS's evaluation earlier — say, immediately after push+email ship, rather than as a distant Phase-3 line — that's a real, worthwhile decision to make explicitly, not something to back into by writing convincingly about it.

## What I'd actually do with this right now

1. **Get an explicit answer on traffic-aware leave-by's tier** before anything else here gets written into a canonical document.
2. **Write the ambient/multi-surface model into the roadmap as a named long-term thesis**, clearly marked as directional rather than committed — it's a legitimate answer to "why Corralio instead of the existing team app," and costs nothing to state as a destination.
3. **Do not change the primary V1 success metric yet.** Keep "weekly returning families" as the measured signal until an ambient-equivalent signal (calendar feed fetch, SMS engagement) actually exists to measure against it — otherwise the org loses the ability to tell whether this thesis is working.
4. **Treat iCal-publish as the one concrete candidate to actually schedule** once 3.6B clears bandwidth — it's the only piece of this update that's buildable today without new evidence, new auth primitives, or a tier decision.
5. **Leave the concierge/manual test from the last review as the actual next step on ingestion.** This document doesn't change that evidence bar, however much more compelling it makes the destination sound.
