## 4. Household origin — capture, geocode, store coordinates only

Add the optional home-address field to the existing household settings surface identified in Section 1's audit, following that surface's established form/server-action pattern. The server action resolves the acting household from the authenticated session itself (Section 1, Section 7) — it never trusts a household ID passed from the client. On save:

- Trim and length-bound the submitted address (match the existing 100-character-class limits used elsewhere in this codebase for user-supplied text, e.g. household/child display names).
- Geocode server-side through one new, narrowly-scoped Corralio-owned helper against the **Geocodio** Geocoding API (confirm the exact current documented endpoint/request shape during Stage 1 rather than trusting this prompt's memory of it — it is a new integration to this repo). `apps/referee`'s Mapbox-based `geocodeAddressMapbox` is not a template to copy for request/response shape — it is only a loose precedent for the general pattern (server-side call, bounding/validation, safe failure) and targets a different vendor. Log through `corralio_external_api_calls`, not `trackExternalCall`.
- **Acceptance rule — both conditions required, not either.** A geocode result is only accepted as a success if it meets **all** of: `accuracy` score at or above `0.8` **AND** `accuracy_type` in an allowed set such as `rooftop`/`point`/`range_interpolation` (confirm Geocodio's exact current field names/vocabulary per Section 1) **AND** the returned coordinates fall within valid global ranges (`lat` between -90 and 90, `lng` between -180 and 180 — belt-and-suspenders alongside the Section 3 CHECK constraints, since app-level validation should reject bad data before it ever reaches the database) **AND**, if Geocodio's response includes a country/region code, it matches an expected set (recommend `US` only for V1, consistent with every other US-specific assumption already in this codebase — flag this explicitly in the Stage 1 report as a V1 scope choice, not a permanent restriction). A high numeric score alone (e.g., a well-scored city-centroid match) or an allowed type alone (e.g., a nominally "rooftop" result with a low confidence score) is **not** sufficient on its own — both the score and the type must clear the bar together. A result failing any of these checks is a **definitive failure**, not a success — do not store imprecise or implausible coordinates as if they were a usable origin.
- **Retryable vs. definitive failure.** A transient failure — network error, timeout, HTTP 5xx, HTTP 429 rate-limit, or a malformed/incomplete provider response that may succeed on a later request — is retryable: leave `origin_lat`/`origin_lng`/`origin_geocoded_at`/`origin_geocode_failed_at` all null so a later save/attempt tries again, and log it with `retryable: true`. A definitive failure — a structurally valid response with no results, or a structurally valid result failing the acceptance rule above — sets `origin_geocode_failed_at` and leaves lat/lng null, logged with `retryable: false`; locally detected malformed input that will not change on retry is also definitive. Do not retry a definitive failure automatically. Either way, do not raise a hard form error — tell the parent the address couldn't be located and that leave-by won't be available until it's corrected, but let the save succeed for the rest of the settings form if there is one.
- **Changing or clearing the origin.** Whether the household clears the address entirely or replaces it with a different one, null out `origin_address`/`origin_lat`/`origin_lng`/`origin_geocoded_at`/`origin_geocode_failed_at`/`origin_geocode_claimed_at` together in the same write before attempting to geocode the new value (if any). In the same authenticated server-side operation, invalidate every event route owned by that household by clearing `estimated_drive_minutes`/`route_distance_meters`/`route_provider`/`route_failed_at`/`route_claimed_at`/`leave_by_computed_at`; preserve the event-location geocode fields because the destinations did not change. This eager route invalidation is required even though Section 6 also has a render freshness gate: `route_failed_at` has no independent origin-version timestamp, so retaining it after an origin change would permanently block a route that may succeed from the new origin. A changed (not cleared) origin then re-geocodes exactly as a fresh save would, and routes recompute lazily on subsequent qualifying mounts.
- **Never store, log, expose, or return the raw geocoding API response.** Store only `origin_lat`/`origin_lng`/`origin_geocoded_at` on success, per above. Do not put the address or coordinates in any log line, error message, `error_code` value, or the Slice 4.2A weekly-engagement telemetry.
- The stored `origin_address` text itself is bearer-like-sensitive PII, more sensitive than a calendar URL: it identifies where a family lives. Confirm RLS already scopes `corralio_households` to household members only (it does, from the Slice 2 foundation) and that no existing authenticated-read policy or view exposes `origin_address`/`origin_lat`/`origin_lng` beyond the owning household. Add an explicit column-level protection only if the audit shows a broader existing grant than household-scoped RLS already provides — check before assuming you need to add anything beyond what RLS already does.
- **Household origin is never venue evidence.** The submitted origin address, its normalized form (if one exists only transiently during request processing), coordinates, geocode metadata, and any routes derived from it are private household inputs used only for that household's leave-by calculations. Never copy them into, expose them to, or consult them from canonical venue matching, venue evidence, venue confidence, tournament intelligence, cross-household location caches, or any Slice 4.4 venue/POI system. Event-location coordinates may later participate in Slice 4.4 only under that slice's separately reviewed rules; household-origin data may not.

## 5. Event geocoding — lazy, deduplicated across the whole household, batched, and bounded

Do not geocode every event eagerly on ingestion or on every page render — that is both unbounded cost and unnecessary for events the household never actually views on `This Weekend`. The server resolves eligible events itself, scoped to the session-derived household; it never trusts a client-supplied event list (Section 1, Section 7).

Geocode an event's location only when all of these hold: the household has a successfully geocoded origin; the event falls in the current `This Weekend` candidate window; the event has non-empty `source_location_text` or `display_location_text`; and the event does not already have `location_geocoded_at` or `location_geocode_failed_at` set (never re-geocode a location that already resolved or already definitively failed — a changed event location should get a fresh geocode attempt, see "changed location" below). Use the same Geocodio helper and acceptance rule as Section 4.

**Reuse before deduplicating, deduplicate before calling the vendor.** Normalize every eligible event's location text into `location_normalized` (trim, case-fold, collapse whitespace) as soon as it's known, independent of whether the event has been geocoded yet. Before calling Geocodio for a given normalized location:

1. First check whether the household already has *any* other event — geocoded in a previous mount, not just this batch — with the same `location_normalized`. If one has a successful result, copy its `location_lat`/`location_lng` and source `location_geocoded_at` onto the new event, clear the new event's failure/claim fields, make no vendor call, and log `status: 'skipped'`, `billable: false`, `error_code: 'household_result_reused'`. If one has a definitive `location_geocode_failed_at`, reuse that terminal outcome in the same way rather than paying to retry the same definitively rejected normalized location for every newly added event. This is what makes "geocode once per unique address per household, ever while that reusable household evidence remains stored" actually true — grouping only within the current mount's batch misses every case where the matching event was added and resolved in a prior mount.
2. Only for normalized locations with no existing household result, group the remaining eligible events by `location_normalized` and make one Geocodio call per unique group, applying the result to every event in that group. Every worker derives the same deterministic representative (the lowest eligible event UUID under a stable ordering), attempts to claim only that row, and skips the whole group if that claim is not acquired—never fall through to another group member. Log calls saved within the batch as `status: 'skipped'`, `billable: false`, `error_code: 'batch_duplicate_skipped'` rows.

**Changed location.** When an event's location text changes (replaced/updated ICS import, manual-event edit), clear `location_lat`/`location_lng`/`location_normalized`/`location_geocoded_at`/`location_geocode_failed_at`/`location_geocode_claimed_at`, recompute `location_normalized` from the new text, and — in the same write — also explicitly clear `estimated_drive_minutes`/`route_distance_meters`/`route_provider`/`route_failed_at`/`route_claimed_at`/`leave_by_computed_at`. Do not rely solely on Section 6's "cached value newer than geocode timestamps" comparison to catch this: once `location_geocoded_at` is nulled out, comparing a timestamp against null does not reliably evaluate as "stale," and Section 6's render gate specifically needs both fields present to compute freshness. Clearing both sets of fields together at the moment location text changes is the actual complete invalidation rule.

Trigger this from the same real-mount pattern established in Slice 4.2A's weekly-engagement write (Section 6 there): once per real `This Weekend` mount, client-triggered, never from server render or prefetch. Cap the number of *unique normalized locations requiring a new Geocodio call* (after the household-reuse and batch-dedup steps above) per mount at `EVENT_GEOCODE_CAP_PER_MOUNT = 10`, so one household with many ungeocoded events in view cannot trigger an unbounded burst of Geocodio calls from a single page load; geocode the remainder on a subsequent mount. This per-mount cap is a client-triggered shaping mechanism, not the enforcement boundary — Section 7's server-side daily cap is what actually bounds cost regardless of client behavior.

## 6. Drive duration and leave-by — one routing call per qualifying unique route, capped per mount

**Routing is reused and deduplicated the same way geocoding is.** Because V1 has exactly one household origin, two events sharing the same `location_normalized` also share the same origin→destination pair. Before calling OpenRouteService, look across the session-derived household for an event with the same `location_normalized` and a route result fresh against the household's current `origin_geocoded_at` and that location's current geocode timestamp. Reuse a fresh successful result (`estimated_drive_minutes`/`route_distance_meters`/`route_provider`/`leave_by_computed_at`) or a fresh definitive `route_failed_at` terminal outcome across matching events with no vendor call, logging `status: 'skipped'`, `billable: false`, `error_code: 'household_result_reused'`. Only when no reusable prior result exists should the server route once per remaining unique normalized location and apply the result to every matching event. For each group, derive the same deterministic representative—the lowest eligible event UUID under a stable ordering—claim only that row, and skip the whole group if the claim is lost; never fall through to another event in the group. This avoids duplicate calls both across prior mounts and within the current batch.

For each unique routed location that has both a successfully geocoded household origin and a successfully geocoded event location, and no cached `estimated_drive_minutes`/`leave_by_computed_at` newer than the geocode timestamps on both ends, and no `route_failed_at` set: call the routing provider (OpenRouteService, per Section 1, at `api.heigit.org/openrouteservice/v2/directions` — confirm the exact current documented request/response shape during Stage 1, this is a new integration to this repo), non-traffic `driving-car` profile only, origin = household coordinates, destination = the location's coordinates. Isolate this HTTP call in one small helper so the provider can be swapped later without touching the surrounding leave-by logic. Cap the number of unique routes computed per mount at `MAX_ROUTES_PER_MOUNT = 10`, applied after the dedup above — state both this cap and `EVENT_GEOCODE_CAP_PER_MOUNT` explicitly and separately in the Stage 1 report; do not describe routing calls as "already counted in" the geocode cap, since a household can have far more already-geocoded, not-yet-routed events in one mount than it geocodes in that same mount (e.g., after a period where routing calls were failing transiently while geocoding kept succeeding). Route the remaining unique locations on a subsequent mount.

On a successful call, store the resulting duration (rounded to the nearest minute) in `estimated_drive_minutes`, the resulting distance (rounded to the nearest meter) in `route_distance_meters`, the provider name in `route_provider`, and set `leave_by_computed_at`, applied to every event sharing that `location_normalized`. On failure, distinguish retryable from definitive exactly as geocoding does: a transient failure (timeout, HTTP 5xx, HTTP 429, or a malformed/incomplete/unusable provider response that may succeed on a later request) is retryable — leave `estimated_drive_minutes`/`route_distance_meters`/`route_provider`/`route_failed_at`/`leave_by_computed_at` all null, log `retryable: true` with the applicable constant `error_code`, and let a later mount retry. A definitive failure is limited to a valid provider response establishing that no route exists between the accepted coordinate pair, or locally detected malformed input that will not change on retry; it sets `route_failed_at` and logs `retryable: false`. Do not auto-retry a definitively failed route on every subsequent mount.

**Render gate must match the recompute-trigger freshness check, not just the recompute trigger.** Render the leave-by line only when all of: `estimated_drive_minutes` is present; the household origin is set; and `leave_by_computed_at` is not older than either `origin_geocoded_at` or `location_geocoded_at`. That third condition is not optional or redundant with the recompute trigger — without it, the moment a household changes its origin address, every event's *previous* cached `estimated_drive_minutes` (computed against the old origin) remains non-null and would otherwise render as if still valid, right up until the next mount's recompute finishes. The freshness check that decides "should I call the routing provider again" must be the exact same check that decides "should I render this cached value," or there is a window where a stale, wrong leave-by time is shown as if it were current.

Render the leave-by line, labeled visibly as an estimate: `event.starts_at − estimated_drive_minutes − LEAVE_BY_ARRIVAL_BUFFER_MINUTES = leave-by time` (e.g. "Leave by 6:55 AM (est.) · ~52 min drive"). Never render a bare, unlabeled leave-by time, and never render a stale one per the gate above.

This is best-effort, additive UI, exactly like Slice 4.2A's telemetry write: a failed or slow geocoding or directions call must never block the event card from rendering its existing title/time/location/conflict information, and must never throw into the render path.

## 7. Cost governance — server-enforced and atomic, not just client-shaped

Every prior Corralio external call (schedule ICS fetch) is bounded by one connected source per team/child and a scheduled refresh cadence. Geocoding and directions calls are shaped differently — they scale with events-in-view, which scales with connected schedules and time — so this slice needs layered, genuinely enforced protection:

**Authorization boundary.** Every server action or route this slice adds must resolve the acting household from the authenticated session itself, exactly like every prior Corralio server action already does. It must never trust a client-supplied `household_id`, event ID list, geocoding candidate list, or cap/limit value — client input may only select among what the server has already scoped to that session, never expand or override the server-resolved set or the caps below (Section 1, Section 4, Section 5).

**Client-side shaping caps** (`EVENT_GEOCODE_CAP_PER_MOUNT`, `MAX_ROUTES_PER_MOUNT`, Section 5/6) that keep a single page load from firing an unreasonable burst. These alone are not sufficient — a client bug, a rapid remount loop, or multiple open tabs can bypass a purely client-side cap, and a household with a large backlog of already-geocoded-but-unrouted events could still generate many mounts' worth of calls over a session even with a per-mount cap in place.

**A server-enforced daily household cap, reserved atomically before each vendor call — not checked-then-acted.** A plain "query today's count, then decide" check is a race: two concurrent requests (different events, same household, same moment) can both observe a count under the limit and both proceed, overshooting it. Instead, reserve capacity atomically using `corralio_external_call_daily_quota` (Section 3) immediately before every real Geocodio or OpenRouteService call — one reservation per intended vendor call, never batched:

```sql
insert into corralio_external_call_daily_quota (household_id, quota_date, reserved_count)
values ($household_id, current_date, 1)
on conflict (household_id, quota_date)
do update set reserved_count = corralio_external_call_daily_quota.reserved_count + 1
where corralio_external_call_daily_quota.reserved_count < $cap
returning reserved_count;
```

Proceed with the vendor call only if this statement returns a row. If it returns no row, the household is at its cap for the day: skip the call, treat the affected event(s) exactly like any other failure for that mount (no leave-by, no error surfaced to the parent), and log a `billable: false` row with `error_code: 'daily_cap_reached'` in `corralio_external_api_calls` — but do **not** touch `corralio_external_call_daily_quota` for that skip; only an actual attempted vendor call reserves quota, so a blocked or dedup-skipped attempt never itself consumes capacity. Set `CORRALIO_DAILY_EXTERNAL_CALL_CAP_PER_HOUSEHOLD = 50` for `$cap` (comfortably above one real mount's worst case across origin + both per-mount caps, but low enough to catch a runaway client) and state the exact value in the Stage 1 report.

**Concurrency protection for individual rows and normalized-location groups**, distinct from the household-wide quota above: before calling the vendor for a household origin, atomically claim that household row. For an event geocode or route group, all workers must query the same household-scoped eligible set using a stable ordering, select the lowest eligible event UUID as the sole representative, and attempt to claim only that representative row with `UPDATE ... WHERE ... RETURNING id`. Only proceed if the claim returns that row. A worker that loses the representative claim skips the whole normalized-location group, logs `status: 'skipped'`, `billable: false`, `error_code: 'concurrent_claim_skipped'`, and must not select or claim a different event from it. This prevents two concurrent requests from choosing different group members and both calling the vendor for the same normalized location. Use the existing two-minute stale-claim recovery condition so a crashed request self-heals. Acquire the row/group claim first, then make the atomic household quota reservation immediately before the vendor call; losing a row/group claim never reserves quota. The row/group claim does not protect the household-wide daily total—that is the separate quota reservation's job.

Beyond the above:

- State, in your Stage 1 report, the maximum number of Geocodio geocoding calls plus directions calls one household's single `This Weekend` mount can trigger: at most `EVENT_GEOCODE_CAP_PER_MOUNT` (10) new geocodes, plus at most `MAX_ROUTES_PER_MOUNT` (10) new routes, plus at most one origin geocode per settings save — stated as separate numbers, not one folded into the other — and separately state the server-enforced daily ceiling (50) from above.
- Log every Geocodio geocoding call, every directions call, and every blocked/skipped/reused attempt (household-reuse skip, batch-dedup skip, daily-cap block) through `corralio_external_api_calls` (Section 3), tagged with the correct `api`, `household_id`, `billable`, `retryable`, and `error_code` values, with enough detail to compute per-household and total call volume, but no address text or coordinates in `error_code` or anywhere else in that table.
- Do not build a dashboard or alerting for this in this slice — one read-only manual SQL script is enough (Section 8), matching the Slice 4.2A report-script convention.
