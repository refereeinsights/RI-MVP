# RefereeInsights Travel MVP — Local Completion Report

Date: 2026-08-28

## Outcome

RefereeInsights now has a focused `/travel` experience for an official looking for a room near an assignment. It supports manual destination search and trusted canonical-venue entry through `?venue_id=`, renders sanitized HotelPlanner results inline, and hands every property selection to TI's existing attributed `/go/hotels/property` route. It does not become a general travel marketplace and does not add booking, group-block, rental, search-platform, or negotiated-rate architecture.

## Audit decisions

- The TI generic-search restriction was a surface/anti-abuse allowlist, not a product or security rule unique to Book Travel and Weekend Planner. Exact `referee_travel` was added; arbitrary sources remain rejected.
- RI's server-side searches share the TI rate-limit identity because the current limiter is IP/user-agent based. Existing bounds remain 5 requests per 5 seconds and 30 per minute. Expected MVP traffic is safe, but this is a documented aggregate capacity ceiling. No global limit weakening, spoofable forwarded-client-IP trust, schema, auth framework, or distributed limiter was added.
- RI request source and flow are `referee_travel`. The existing attribution implementation intentionally canonicalizes HotelPlanner/source-page context to `referee`; `Custom8` remains `app:refereeinsights`, and `Custom3` is generated by the trusted property handoff.
- The prior deterministic booking reconciliation code existed but was no longer used by the current summary. It was restored without creating a second system.
- No reusable structured-data helper matched this narrowly scoped page, so optional JSON-LD was omitted rather than improvised.

## Privacy and attribution

- Generic destination text is sent only in the same-origin POST body and through the existing TI provider session contract.
- It is absent from `/travel` query parameters, travel analytics, application logs, new RI persistence, and property handoff URLs.
- Analytics vocabulary is exactly `ri_travel_page_viewed`, `ri_travel_search_submitted`, and `ri_travel_results_returned`, with only `mode`, optional canonical `venue_id`, and bounded `result_count` beyond existing base fields.
- The persisted TI outbound row remains the authoritative click/handoff record. Tracking persistence retains the existing fail-open redirect behavior.
- Confirmed booking categories are matched, orphaned valid token, missing token, and invalid token. Matched requires the persisted outbound join. A lookup error marks reconciliation unavailable and suppresses derived conversion while preserving all booking totals.
