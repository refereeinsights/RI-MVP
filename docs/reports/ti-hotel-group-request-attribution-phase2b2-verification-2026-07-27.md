## TI-side chain verification

### 1. Token creation

Verified locally:
- Book Travel / Weekend Planner form mints `outbound_attribution_id` when the journey starts.
- venue-map team-block flow mints `outbound_attribution_id` when the request journey starts.
- retries reuse the same token while the form remains in-progress.

### 2. Internal persistence

Verified in route logic:
- `/api/lodging/group-request` persists one canonical TI record to `lodging_search_session`.
- the canonical TI record stores:
  - `outbound_attribution_id`
  - `source_page_type`
  - `source_path`
  - `cta_placement`
  - `planner_session_id`
  - `tournament_id`
  - `venue_id`
  - `job_code`
  - `keyword`
  - `partner_source_code`
  - `custom_field1` … `custom_field8`
  - `provider_request_snapshot`

### 3. Duplicate handling

Verified in route logic:
- if an existing row with the same `outbound_attribution_id` is already `succeeded`, the route returns the existing TI record instead of creating a second canonical success record.
- if an existing row with the same `outbound_attribution_id` exists but is not yet successful, the route updates that row and reuses it.

### 4. Provider payload construction

Verified through tests and direct code inspection:
- provider payload is built through `buildGroupRequestBody()`
- token and attribution fields are generated by `buildHotelPlannerGroupRequestAttribution()`
- final TI-generated payload uses:
  - `customField3 = attr:<token>`
  - `customField4 = srcp:<source_page_type>`
  - `customField5 = place:<cta_placement>`
  - `customField6 = plan:<planner_session_id>` when applicable
